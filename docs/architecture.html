架构

单仓库、双二进制的 Go 分层单体：约 8.3k 行源码（另有 1.3k 行测试），UI 栈构建在 Charm 家族（Bubble Tea + Lipgloss + Glamour）之上，其余为标准库 + 自研包。零数据库、零云端依赖 —— 会话是本地 JSON 文件，长期记忆是一个 Markdown 文件。本文对应 v0.4.2 源码，每个小节都可直接在 internal/ 里找到对应实现。

2. 运行时形态：两个入口

二进制入口生命周期
hearth（~21MB）cmd/hearth/main.go加载配置 → provider.EnsureBackend（自动发现）→ 构建 tui.App → Bubble Tea Program.Run() 事件循环
hearth-agent（~11MB）cmd/hearth-agent/main.goflag 解析 → cli.RunAgent / Ask / Models，单次执行即退出；不 import 任何 Bubble Tea 包

两者共享同一条 agent → core → provider 链和同一份配置 / 会话 / 记忆，因此 hearth-agent 的运行结果（长期记忆、会话文件）与 TUI 完全互通。

3. TUI 内部（internal/tui，~3.1k 行）

3.1 App 模型与按键路由

整个界面是一个 Bubble Tea Model（App 结构体）。handleKey 按固定优先级路由按键，先到先得：

quit(ctrl+c×2) → 面板(审批/确认/重命名/帮助/列表) → 全局快捷键
→ 滚动(pgup/pgdn/end) → 斜杠弹窗(↑↓/tab/esc) → 输入框(enter/历史/@)

面板共 8 种：panelApproval（工具审批对话框）、panelConfirm（危险操作确认）、panelRename、panelHelp，以及共用 listPanel 的模型 / 会话 / 命令面板 / 文件选择四种列表（支持输入过滤、↑↓/ctrl+n/p 移动、enter 选中）。

输入框是 bubbles 的 textarea：Enter 发送、Alt+Enter/\+Enter 换行、空输入按 ? 打开帮助、@ 打开文件选择器、输入以 / 开头时弹出斜杠命令弹窗（8 行滚动窗口 + 位置指示，↑↓/滚轮选择、tab 补全、esc 收起）。

3.2 渲染管线（render.go + stream.go）

网络 goroutine → buf.Add(增量) → deltaBuf(mu 保护)
    Total(): 累计全文（组装最终消息）
    Drain(): 待刷尾部 ←—— 50ms ticker → prog.Send(deltaMsg) → Update → refreshContent

关键点：

  • 渲染节流：流式增量不逐帧重绘，由 50ms ticker 批量刷进 UI（PRD 渲染节流）；回合结束后一次性从 Total() 组装完整消息入库。状态栏的实时 tok/s 分母是生成活跃时间（相邻增量间隔 <2s 才计入）—— 工具执行的零输出时间不计入，否则长 agent 任务的回合平均速率会被稀释到个位数。
  • 渲染缓存：renderer.cache 以 (消息下标, 内容长度) 为键 —— 会话消息一旦写入不可变，已完成块只渲染一次；流式中的回复走 liveBlock 纯文本，不经 glamour，且换行增量推进（append-only 流每行只排一次，不再每帧全量重排 —— 长回复后期 16× 提速）。拼接层再加会话前缀缓存（append-only，边界消息时间戳 + 宽度自校验）与相同内容跳过 SetContent —— 长会话流式帧从全量 Join（实测 2.1ms/2717 次分配每帧）降到仅拼接尾部（0.11ms/1 次）。
  • Markdown：只有已完成的 assistant 消息用 glamour 渲染（宽度变化时惰性重建 renderer），缓存失效场景：窗口 resize、裁剪、模型切换、会话切换（Invalidate()）。
  • thinking 流：只显示最后 4 行暗色文本，不参与 Markdown 渲染。

3.3 回合生命周期（app.go startTurn → onDone）

发送前守卫: UsedTokens > 90% numCtx → TrimToMax 预裁剪
  → 用户消息入 Session → saveSession（原子写）
  → agent 模式 ? startAgentTurn : startChatTurn（各自起 50ms flusher + 网络 goroutine）
  → 事件循环（deltaMsg / agentEvtMsg / doneMsg）
onDone: 错误分类处理 → AutoTitle → saveSession
  → 85% 自动压缩检查（仅成功回合 —— 失败回合不压缩,证据不被摘要抹掉,
     状态栏持续显示 ✗ 任务失败原因,而非只闪 4 秒的 toast）
  → pendingSends 队列（busy 时输入排队，150ms 后逐条回放）

错误自愈：连接错误熄灭右上角 ollama 指示灯；404 触发"did you mean"模型名建议（SuggestModels 打分）；上下文溢出回滚本轮（PopLastUserTurn）、裁剪历史、自动重发一次。生成中 Esc 取消 context，已到的部分输出保留并标记 interrupted。

3.4 @ 文件引用与多模态

refs.go：@path#L121-135 正则解析 → 文件选择器（跳过 .git/node_modules/vendor 等 13 类目录，上限 500 文件）→ 发送时快照内容存入 FileRef.Content（后续编辑不影响已发内容），API 发送时展开为带行号的上下文块。图片走 base64 进 Message.Images，模型无 vision 能力时行内提示。

4. Agent 内核（internal/agent，~800 行）

4.1 Run()：单 goroutine 事件流

Agent.Run(ctx) 返回 <-chan Event：内部 goroutine 跑完整个工具循环，7 种事件（EvThinking / EvContent / EvToolStart / EvToolResult / EvApproval / EvTurnDone / EvError）经 64 缓冲 channel 推给消费者（TUI 或 CLI），channel 关闭即回合结束。取消 = 取消 ctx，部分输出照常入库。

4.2 工具循环

for step := 0; step < MaxSteps(默认25); step++ {
    streamTurn(): 流式收集 content/thinking/原生 tool_calls
    ├─ 无原生调用 → 文本协议 fallback 解析
    ├─ 无任何调用 → 自然完成，EvTurnDone 收尾
    ├─ 溢出错误  → TrimToMax 裁剪后 step-- 重试（不耗预算）
    └─ 逐个执行工具 execTool()（权限拦截 → 执行 → 结果入库）
    步间守卫: 估算 > 90% 窗口 → 轮内裁剪并发 EvTrimmed（压缩仍等回合结束）
    倒数第二步执行后发 "step budget: n/25 used — wrap up soon" 提示
}
预算耗尽 → 追加一条临时 system 消息，禁用工具再调一次：只许总结收尾

4.3 双通道工具调用解析

小模型经常不按原生 tool_calls 通道出牌，parseTextToolCalls 兜底三种文本格式（解析后从正文剔除）：<tool_call>{...}</tool_call> 标签、```json / ```tool_call 围栏、整段裸 {"name","arguments"} JSON；arguments 兼容对象和 JSON 字符串两种形态。

4.4 上下文组装 apiMessages()——前缀缓存友好的布局

[system] 会话系统提示 + 紧凑 agent 规则（10 条，≤1 屏）   ← 稳定前缀，命中缓存
[system] SystemHint（headless 场景附加）                  ← 稳定
[user / assistant / tool …] 完整历史                      ← 步间不变，命中缓存
[system] 尾部易变注入：Session notes(≤1200字符) + 长期记忆(最近8条) ← 每步重算

易变内容（草稿本、记忆）放在消息尾部而非系统提示，使每步只重新评估一个小后缀，历史前缀持续命中 Ollama 前缀缓存 —— 实测多步 agent 壁钟 -22%。另有上下文卫生：从尾部数第 7 条起的旧工具结果截断到 MaxToolLen/3；thinking 不回传；工具结果超 MaxToolLen(8000字符) 截断。context 的运行时载体与持久化位置见 8.6 节。

4.5 流式与自愈

streamTurn 请求带显式 Think: true/false；服务器报 "does not support thinking" 时自动去掉该 flag 重试一次。小模型可能把最终回答只写进 thinking 字段 —— 完成路径会把它提升为正文（已完成消息不渲染 thinking，否则回答"隐形"、转录像无故停在最后的工具结果）；完全空响应标记 Usage.Failed 并发 EvError，状态栏持续显示 ✗。回答被 num_predict/num_ctx 截断时（done_reason=length），消息尾部显示截断标记并 toast 提示调整 —— 截断的回答不再伪装成完整回答。用量统计取自服务端字段（PromptEvalCount / EvalCount / EvalDuration），TPS = 输出 token ÷ 服务器实测生成时间，而非壁钟。

5. 权限管理器（agent/perm.go）

5.1 判定顺序（NeedsApproval）

deny_patterns 命中(含内置14条强制正则) → 强制弹审批（full 模式也不例外）
→ 会话级已批准(tool) → 放行
→ read 类工具 → 放行
→ auto_approve 配置 → 放行
→ 按 mode: full 放行 / risky 白名单判定 / ask 一律弹

审批交互是同步的：ApprovalRequest 带 Respond chan ApprovalDecision，UI 弹对话框用户按键后 Decide()（once / session / deny），channel 容量 1 且 recover() 保护 —— UI 已关闭时发送不会 panic。

5.2 三档语义

档位bashwrite/editmemory_save其他变更
ask弹审批弹审批弹审批弹审批
risky只读白名单自动工作目录内自动自动弹审批
full自动自动自动自动（deny 仍拦）

白名单 42 条只读前缀（ls/cat/grep/git status/…含 PowerShell 的 get-childitem 等）；链式命令（| ; &&）逐段校验，任一段不在白名单即弹审批。强制正则覆盖 rm -rf、mkfs、dd of=/dev/、fork bomb、sudo、curl|sh、git push -f、del /s、format C:、remove-item -recurse 等 14 类。工作目录判定用 filepath.Rel 防御 ../ 逃逸。别名归一：standard→ask、yolo→full（CLI 的 --yolo 即此）。

6. 工具系统（internal/tools，~1.7k 行）

6.1 结构

工具是纯数据描述 + 函数指针：Tool{Name, Desc, Schema(JSON Schema), Category(read/mutate/exec), Fn}。Registry 持有工作目录、超时、shell 偏好与可选的 Session / Memory / Search 接线，All() 按系统提示展示顺序返回 13 个工具。TUI /config 或模式切换后 syncRegistry() 重新接线。

7. Provider 层（provider/ + ollama/）

7.1 Client 接口

5 个方法（ChatStream / Chat / Tags / Show / Ping），参数与返回值全部使用 ollama 包的规范类型 —— OpenAI 兼容客户端在边界做双向翻译，上层（agent/tui/cli）对后端差异零感知。

7.2 工厂与风格识别

api_style: auto 按 URL 形状识别（/v1 结尾 → openai）；ollama 模式下 URL 误带 /v1 会被容忍剥离；openai 模式缺 /v1 自动补全。

7.3 ollama 原生客户端（client.go）

  • /api/chat NDJSON 流：bufio.Scanner 8MB 行缓冲（thinking 块可能很长）。
  • num_ctx 推送：每次请求都携带 options.num_ctx（来自会话参数 /ctx 或配置 context.num_ctx，默认 16384）—— 不推则 Ollama 落回自己的服务端默认（2048/4096，视版本），窗口会被砍小。
  • 错误分类：ModelError{Status,Body} + IsNotFound(404) / IsContextOverflow(body 含 context exceed/length/too large/unable to pack) / IsConnError(net/url.Error 系) —— agent 与 TUI 据此走不同自愈分支。
  • 重试：连接类错误指数退避最多 3 次（500ms 起步），且仅在尚未收到任何流块时重试，避免重复输出。

7.4 OpenAI 兼容客户端（openai.go）

  • 请求翻译：options → temperature / top_p / seed，NumPredict → max_tokens；keep_alive 无对应概念即丢弃；消息含图片时按 base64 头嗅探 MIME 拼 data-URI（严格服务器校验媒体类型）。
  • num_ctx 不对称：OpenAI Chat Completions 协议没有上下文窗口参数，NumCtx 在翻译时被丢弃、不发送 —— 接 LM Studio / llama.cpp / vLLM 时真实窗口由后端服务自己的配置决定；hearth 的 16384 此时只用于内部记账（90% 预裁剪 / 85% 自动压缩的触发基准与状态栏 ctx 仪表），若与后端实际窗口不一致，估算会偏离现实。原生模式则每请求推送（见 7.3）。
  • 流式：SSE data: 块解析，[DONE] 终止；tool_calls 分片重组（参数按 index 逐块到达，toolAccum 合并）。
  • 错误体翻译回 ModelError，复用同一套分类助手；模型列表走 /v1/models，Show 用能力探测模拟。

7.5 本地后端自动发现（discovery.go）

候选风格

8. 领域模型与存储（core/ + store/）

8.1 Session 并发模型

Session 内置 sync.RWMutex：agent 循环在自己的 goroutine 里追加消息，UI 线程同时渲染 —— 所有读取走 Snapshot()/Clone() 拷贝出独立切片，写走 Add/SetMessages/TrimToMax。这是整个程序里最关键的共享状态，测试里有并发压力用例。

8.2 Token 估算与裁剪

EstimateTokens 是 CJK 感知启发式：汉字/假名/谚文 ≈ 1 token/字，其他 ≈ 4 字符/token（对中文对话误差远小于按字节估算）。TrimToMax 按预算 ×85% 安全边裁：整轮丢弃（user→assistant 含其间全部 tool 交换），系统提示与最后一轮永远保留。只剩一轮时（超长 agent 任务是一条 user 消息带几十条消息），回退为轮内裁剪：按 assistant→tool 交换组从旧到新丢弃（调用与结果成对不拆散），开头 user 消息与最新一组永远保留 —— 否则单轮 agent 会话会在窗口外卡死、无法自愈。

8.3 会话持久化（store.go）

每会话一个 JSON 文件（DataDir/sessions/<id>.json），tmp + rename 原子写；Save 先 Clone() 再序列化，agent 并发写入不会撕裂输出。Load 校验 id 防路径穿越；List 全目录扫描按更新时间排序。

8.4 双层记忆

层载体生命周期注入方式
短期Session.Scratchpad（note 工具读写）会话内每步注入消息尾部（≤1200 字符）
长期DataDir/memory.md（- [时间] 内容 一行一条）跨会话跨进程每回合注入最近 8 条；memory_recall 按需检索

长期记忆带 sync.Mutex 串行化读写，外部手改文件也能被解析（不识别行整条保留）。

8.5 自动压缩（tui/export.go）

回合成功结束且 UsedTokens ≥ num_ctx × 85% 时触发：compactSummarize 用同一模型做一次非流式总结（保留关键事实/决策/文件路径/待办，跟随对话语言）→ 新消息序列 = [conversation summary] + 压缩期间新增的尾部原文(含相邻一轮完整 user/assistant) + 草稿本 —— 压缩后对话"不断联"。

8.6 上下文与记忆：架构与存储位置

Agent 的 context 没有独立存储——它是每一步从 Session 现场投影出来的视图：apiMessages()（4.4 节）在每个循环步重新组装一次请求消息，会话 JSON 才是唯一事实源。三者的关系：

Session（内存,唯一事实源）
  ├─ Messages []Message     ──apiMessages() 投影──▶ 每步发给模型的 context
  ├─ Scratchpad（短期记忆）   ─────────────▶ 拼进 context 尾部 system 消息
  └─ DataDir/memory.md（长期记忆）────────▶ 取最近 8 条拼进同一处
      │
      └─ store.Save：每回合原子写 ▼
         DataDir/sessions/<id>.json（会话 + scratchpad 字段一并持久化）
内容运行时持久化位置
Agent contextcore.Session.Messages（RWMutex 保护，UI 经 Snapshot/Clone 拷贝读取）会话 JSON 文件；无独立的 context 缓存/向量库/数据库

9. 配置与迁移（internal/config）

  • 路径链：HEARTH_CONFIG 环境变量 → 用户配置目录 hearth/ → 用户配置目录 ollama-tui/（旧品牌）→ 家目录点文件（新旧两种）。惰性迁移：旧 ollama-tui 的配置与会话目录存在就继续沿用，Save 永远写新主路径。
  • normalize 钳制：加载后统一夹取合法区间（num_ctx ≥ 2048、CompactAtPct 50–100、温度 0–2……），非法权限档/主题/引擎归一为默认值，配置文件手写坏值不会引发运行时异常。
  • 热重载：TUI 内 /config 在 $EDITOR 打开文件，保存退出后 configReloadedMsg 重建 perms/memory/registry/主题，无需重启。
  • 数据目录：DataDir() 同样有新旧品牌链 + HEARTH_DATA 环境变量覆盖；会话在 DataDir/sessions/，长期记忆在 DataDir/memory.md。
